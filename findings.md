# ML in Snowflake — probe + spike findings

Date: 2026-11-09 · Account `IVANTAGE` (Azure East US 2) · Role `HAT_DATASCIENCE_ANALYST` · Warehouse
`HAT_DATASCIENCE_WH` (standard, X-Small) · Scratch schema `HAT_DATASCIENCE_DB.ML_SPIKE_SCRATCH`.
All data is synthetic (`MOCK_CLASSIFICATION`, `MOCK_REGRESSION`, 5,000 rows each, generated by
`mock_data.py`). Raw outputs are in `output/*.json`.

## TL;DR

1. **Scoring in Snowflake works today with no new privileges.** Native sklearn and XGBoost models
   registered in the Snowflake Model Registry score in the warehouse with exact parity to local
   (max abs diff ≤ 2e-9, 0 label mismatches).
2. **Training in Snowflake from the local IDE works today**, including a **custom XGBoost objective**,
   both via `snowflake.ml.modeling` and via a stored procedure. Parity with local training is exact
   (diff 0.0). There are three sharp edges, listed below.
3. **Snowflake Experiment Tracking works** for params, metrics (including stepped metrics), and model logging.
   Combined with the Registry, it covers what we wanted the Azure MLflow server for. **Recommendation: do
   not request the Azure MLflow resources yet.** Keep local MLflow (sqlite) optional for dev. If a model
   comes from MLflow, promote the *native flavor*, not the pyfunc wrapper.
4. The account has **no compute pools visible, no Snowpark-optimized warehouse, no external access
   integrations, and no role with `EXECUTE TASK`.** Those are the IT asks, and none is needed for stages 1–2 at
   toy scale.

## Spike A — MLflow → Snowflake Registry promotion (`spike_a_promote.py`)

Train locally → log to local MLflow (`output/mlflow.db`) → load MLflow version *n* → `Registry.log_model(...,
version_name=f"V{n}", target_platforms=["WAREHOUSE"], options={"relax_version": False})` → `mv.run()` on the
Snowflake table → compare with local predictions. The promotion record is written to `output/promotion_manifest.json`
(MLflow name/version/run id → Snowflake FQN/version + parity). This is the shape the git manifest would take.

| Model | Path | log_model | Warehouse run (5,000 rows) | Parity |
|---|---|---|---|---|
| sklearn LR pipeline | native | 24 s | 27 s | max diff 2.2e-16, 0 mismatches |
| sklearn LR pipeline | MLflow pyfunc | 53 s | 134 s | 0 label mismatches (predict only) |
| XGBClassifier | native | 11 s | 35 s | max diff 1.9e-9, 0 mismatches |
| XGBClassifier | MLflow pyfunc | 13 s | **1st run: internal error after 563 s** (`000603`, incident 8288608). Retry: 131 s | 0 label mismatches on retry |

Takeaways:
- Promotion works, and deterministic `V<n>` version names map cleanly from MLflow.
- **Prefer the native flavor** (`mlflow.sklearn/xgboost.load_model`). It exposes `PREDICT_PROBA` / `DECISION_FUNCTION`,
  where pyfunc exposes only `PREDICT`. Native is about 4× faster to score, and native never failed.
- The pyfunc XGBoost failure was a Snowflake-side internal error and did not reproduce. If pyfunc is ever needed,
  raise incident 8288608 with Snowflake support.
- Timings come from a cold X-Small warehouse shared with concurrent spike runs. Treat them as orders of magnitude.

## Spike B — training in Snowflake (`spike_b_train.py`, `spike_b_followup.py`)

Regression on `MOCK_REGRESSION`. The custom loss is asymmetric squared error, with under-prediction weighted 3×
(`custom_losses.py`). Each warehouse result is compared with the identical model trained locally.

| Test | Result |
|---|---|
| (i) `snowflake.ml.modeling.xgboost.XGBRegressor`, built-in objective, fit+predict on Snowpark DF | OK, 107 s. Diff 0.0 |
| (i) …with custom objective **imported from a module** (by reference) | **Fails:** `ModuleNotFoundError: custom_losses` inside the fit sproc. snowml does not ship local modules. |
| (i) …with custom objective after `cloudpickle.register_pickle_by_value(custom_losses)` | OK, 58 s. Diff 0.0 |
| (i) Register fitted snowml estimators (built-in and custom objective) + warehouse run | OK. Diff 0.0 for both |
| (i) `callbacks=` | Not a named parameter, and `fit()` takes only `dataset`, so there is **no `eval_set` and no early stopping**. Callbacks passed via `**kwargs` do reach the fitted xgboost object. Whether they change training was not verified. |
| (i) Transformer-only `Pipeline([StandardScaler])` → `log_model` | **Fails:** `RuntimeError: The meta data is not ready to save.` |
| (ii) Temporary stored procedure (`execute_as="caller"`, `imports=[custom_losses.py]`): `xgb.train(obj=custom)` on `to_pandas()`, then `Registry.log_model(Booster)` **from inside the sproc** | OK. 83 s wall, of which load 0.4 s and train 0.7 s; the rest is env setup and registration. Warehouse inference diff 0.0 vs local |
| Native `XGBRegressor(objective=<callable>)` → `log_model` / `ExperimentTracking.log_model` | **Fails:** `TypeError: argument of type 'function' is not iterable` in `model_task_utils.get_model_task_xgb`. An explicit `task=Task.TABULAR_REGRESSION` **does not** avoid it. |
| …workaround: deep-copy, `set_params(objective="reg:squarederror")` after fit, then log | OK. Diff 0.0. The objective only matters during training. |
| (iii) Experiment Tracking: `set_experiment`, `start_run`, `log_params`, `log_metrics`, stepped `log_metric`, `log_model` | OK. Runs visible via `SHOW RUNS IN EXPERIMENT`. The failed custom-objective attempt left an orphan run `LOCAL_FIT_CUSTOM_OBJECTIVE`. |

(i) vs (ii):
- **snowml estimators** read most like local code and give distributed-friendly data access. But custom code must be
  pickled by value, and there is no `eval_set` or early stopping. Each `fit` spins up a temporary sproc (about 1–2 minutes of
  overhead on X-Small).
- **The stored procedure** gives full xgboost control (`xgb.train`, `obj=`, `evals`, callbacks, early stopping) and
  explicit `imports=` for our modules, and it can register the model in the same call. Its limit is single-node memory
  (`to_pandas()`). For real data volumes that means a **Snowpark-optimized warehouse**, which we don't have.
- Recommendation: use the **stored-procedure pattern** for training jobs with custom losses, and snowml estimators for
  quick standard models.

## Experiment comparison sweep (`sweep_experiment.py`)

This tests whether Experiment Tracking can stand in for MLflow's run comparison during development. It logs 6
XGBRegressor runs to experiment `MOCK_SWEEP`, sweeping `max_depth` over {2, 4, 6} and `learning_rate` over
{0.05, 0.2} on a 75/25 split. Each run logs params, final `val_rmse` / `val_mae` / `train_rmse`, and
`train_rmse_curve` / `val_rmse_curve` every 10 boosting rounds (20 steps). The best run (D2_LR020, val_rmse 17.33)
also logs its model as `MOCK_SWEEP_BEST_XGB` / `V1` with `metrics=`. The script takes about 90 s end to end;
fitting is local and only the logging goes to Snowflake.

Verified through the API:
- All 6 runs show as FINISHED.
- `list_params` returns the params, **stored as strings**.
- `get_metric_history` returns all 20 curve points per run.
- `show_metrics()` on the model version returns the three final metrics.
- `list_model_versions(run_name=...)` links the run to its model version.

Two things to know:
- **Metrics logged on a run are not copied to the model version.** Pass `metrics=` to `log_model`, or call
  `set_metric`, so they show on the Models page.
- **Without `version_name`, versions get random names** such as `FRIENDLY_ROBIN_2`.

**Not yet judged:** how well the Snowsight Experiments UI compares runs, charts curves, and sorts and filters
compared with MLflow. String params may sort lexically.

## Limits hit / not yet tested

- **Memory:** not stress-tested. Everything ran at 5k rows on standard X-Small. The sproc pattern's ceiling is the
  warehouse node memory, so test at real volume on a Snowpark-optimized warehouse once one exists.
- **Package gaps:** none for our stack on 3.11. Moving to Python 3.12 unlocks xgboost 3.4 / numpy 2.5. A user-level
  python.org install needs no admin rights, but it is not done here.
- **Not tested:** container runtime / notebooks on compute pools (no pools), Tasks (no `EXECUTE TASK`), PyPI
  artifact repository installs, Streamlit runtime default, the Experiment Tracking UI and artifact logging, and
  Private Link.

   decision rather than a privilege request.

   call the Azure MLflow server or other external endpoints. The client-side promotion script needs none.
7. **Azure MLflow resources (Container Apps + Postgres Flexible + Blob):** recommend **holding** the request. Spike B
   shows that Snowflake Experiment Tracking + Registry cover tracking and registry.

## How to run (PowerShell, no admin)

```powershell
py -3.11 -m venv .venv-sfml
.\.venv-sfml\Scripts\python.exe -m pip install -r snowflake_ml\requirements-dev.txt
cd snowflake_ml
..\.venv-sfml\Scripts\python.exe inventory.py         # read-only
..\.venv-sfml\Scripts\python.exe setup_scratch.py     # creates scratch schema + mock tables
..\.venv-sfml\Scripts\python.exe spike_a_promote.py
..\.venv-sfml\Scripts\python.exe spike_b_train.py
..\.venv-sfml\Scripts\python.exe spike_b_followup.py
```

Override the defaults with `SF_CONNECTION`, `SF_ROLE`, `SF_WAREHOUSE`, `SF_DATABASE`, `SF_SCHEMA`.
`channel_versions.py 3.11 <pkg> ...` lists channel versions, and `retry_pyfunc_xgb.py <rows>` re-runs the pyfunc
XGBoost scoring check. Teardown: `DROP SCHEMA HAT_DATASCIENCE_DB.ML_SPIKE_SCRATCH;` (drops the mock tables, models
and experiments).
